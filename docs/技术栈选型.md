# lulu's blog：GitHub Pages 技术栈选型

> 结论先行：**继续用现在的 Astro 方案**。项目里已经有一个能构建通过的雏形（首页 / 学习记录 / 项目 / 关于 / 404、Markdown 内容集合、搜索、深色模式、RSS、sitemap、Actions 部署），换栈意味着把这些重做一遍。
>
> 只有在下面两种情况下才值得换：想要「主题一装就好看、博客功能全都有」（→ Hugo + PaperMod），或者想要「极简、几乎不依赖框架」（→ Eleventy 或手写）。

## 一、先划清 GitHub Pages 的边界

GitHub Pages 只托管**静态文件**（HTML / CSS / JS / 图片 / 字体 / JSON）。没有服务端代码、没有数据库、不能跑 PHP 或常驻 Node 进程。所以任何方案都必须是「本地/CI 构建 → 产出静态文件 → 上传」。[官方限制文档](https://docs.github.com/zh/pages/getting-started-with-github-pages/github-pages-limits)

| 项目 | 说明 |
| --- | --- |
| 免费范围 | 公开仓库在 GitHub Free 计划下免费；私有仓库发布 Pages 需要 Pro / Team / Enterprise |
| 站点数量 | 每个账号只能有 1 个用户/组织站点（`用户名.github.io`），项目站点不限 |
| 体积 | 源仓库建议 ≤ 1 GB；**发布后的站点 ≤ 1 GB** |
| 构建时长 | 单次部署（构建 + 发布）超过 10 分钟会超时 |
| 带宽 | 每月 100 GB 软限制，超量可能被限速（返回 429） |
| 构建频率 | 每小时最多 10 次构建；**使用自定义 GitHub Actions 工作流时此限制不适用** |
| 用途 | 不适合电商、在线业务、敏感交易；纯个人博客完全合规 |
| 域名 | 默认域名免费，自定义域名 + HTTPS 也免费 |

### 两种发布方式（很重要）

| 方式 | 做法 | 特点 |
| --- | --- | --- |
| **GitHub Actions（推荐，本项目已配置）** | 工作流里 `npm run build`，用 `actions/upload-pages-artifact` + `actions/deploy-pages` 上传 | 产物**原样**上线，不经过 Jekyll；不受每小时 10 次构建限制；能跑任意构建命令（Node / Go / Rust 都行） |
| 分支发布 | 把构建产物推到 `gh-pages`（或 `main` / `docs`），在 Settings → Pages 选分支 | 简单但 GitHub 会先用 **Jekyll** 处理一遍：以 `_` 开头的目录（Astro 的 `_astro/`、Next 的 `_next/`）会被丢弃，**必须放一个空的 `.nojekyll` 文件**；且受每小时 10 次构建限制 |

> 也就是说，Astro / Next 这类会在 `dist` 里生成 `_astro/`、`_next/` 的方案，走「分支发布」时要格外小心 Jekyll 的坑；走 Actions 发布则完全没事。

## 二、静态站点生成器：主要可选路线

| 技术栈 | 语言 | 写作格式 | 上手成本 | 构建速度 | 主题/生态 | 最适合 | Pages 适配 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **Astro**（本项目） | TypeScript | Markdown / MDX + 组件 | 中 | 快 | 中等，成熟博客主题偏少 | 既要 Markdown 写作，又想自己写页面、加交互 | 很好（`output: 'static'`） |
| **Hugo** | Go（单文件二进制） | Markdown | 低 | 极快（毫秒级） | **最丰富**，PaperMod / Blowfish / Stack | 「不想折腾，装个主题就开始写」 | 很好 |
| **Hexo** | Node.js | Markdown | 低 | 中（文章多了会变慢） | 中文生态成熟，Butterfly / Fluid | 中文博客、想要现成好看的主题 | 很好 |
| **Jekyll** | Ruby | Markdown | 中（本机装 Ruby 麻烦） | 中 | 主题多但偏老 | 想完全依赖 GitHub 官方文档、最保守的选择 | 原生支持（分支发布时不用自己配构建） |
| **Eleventy (11ty)** | JavaScript | Markdown / 任意模板 | 中 | 很快 | 几乎没有现成博客主题 | 想完全掌控输出、讨厌框架的黑盒 | 很好 |
| **VitePress** | TypeScript / Vue | Markdown | 低 | 快 | 文档主题为主 | 以**文档/笔记**为主，博客是附带 | 很好 |
| **Docusaurus** | TypeScript / React | Markdown / MDX | 中 | 中 | 文档生态强，博客是配角 | 项目文档 + 少量博客 | 很好 |
| **Next.js（静态导出）** | TypeScript / React | MDX | 高 | 中 | 丰富但要自己拼 | 以后想加服务端功能、动态接口 | 可行但偏重，`_next/` 目录要注意 Jekyll |
| **Nuxt（静态生成）** | TypeScript / Vue | Markdown / Vue | 高 | 中 | 丰富 | Vue 技术栈、以后要接 API | 可行但偏重 |
| **Zola** | Rust（单文件二进制） | Markdown | 中 | 极快 | 较少，社区小 | 喜欢 Hugo 的速度但讨厌 Go 模板语法 | 很好 |
| **Gatsby** | JavaScript / React | MDX | 高 | 慢 | 生态在萎缩 | 不建议新项目选 | 可行 |
| **无框架** | HTML/CSS/JS | 手写或简单模板 | 低到中 | 无需构建 | 无 | 只有几页、完全不想维护依赖 | 最好（直接推到 `docs/`） |

### 每种路线的真实取舍

- **Hugo**：Go 模板语法晦涩，但换来的是「零依赖 + 极快 + 主题最多」。想少写代码、多写文章，它是最省心的。
- **Jekyll**：GitHub Pages 的「亲儿子」，文档最全；代价是本地要装 Ruby 环境，主题生态偏旧。
- **Hexo**：中文资料最多，主题（Butterfly）开箱很漂亮；代价是依赖多、文章多了构建慢。
- **Astro**：介于「文档框架」和「手写网站」之间——Markdown 写内容、`.astro` 写页面、需要交互时可以只给某个组件挂 React/Vue/Svelte（岛屿架构，其余仍是纯静态 HTML），首页默认零 JS。代价是博客的标签页、分页、相关文章这类功能要自己搭（本项目已经搭好了）。
- **Eleventy**：最自由，几乎没有约定，适合愿意自己写模板的人；代价是没有现成主题。
- **VitePress / Docusaurus**：定位是文档站，博客功能（标签、RSS、封面）都要二次开发，除非你的内容本来就是笔记/文档。
- **Next/Nuxt/Gatsby**：为「以后可能要动态功能」付的税，纯博客属于重型方案。

参考横向对比：[开源博客框架横向对比（2026）](https://jackylee3362.github.io/post/2026/260728-02-blog-framework-compare/)、[Astro vs Eleventy vs Hugo vs Jekyll vs Gatsby in 2026](https://gautamkhorana.com/blog/static-site-generators-2026-astro-eleventy-hugo-jekyll-gatsby/)。

## 三、内容与写作方式（和生成器相互独立，可以自由组合）

| 方案 | 做法 | 适合 |
| --- | --- | --- |
| **仓库里的 Markdown**（本项目） | 一篇 `.md` = 一篇文章，`git push` 即发布 | 会写代码 / 用 Git 的人，最稳、可回溯 |
| Git 型 CMS | Decap CMS、Sveltia CMS、TinaCMS，在浏览器里写，自动提交到仓库 | 想在手机上写、或不想碰命令行 |
| 外部内容源 | Notion / 飞书文档 / Contentful / Sanity，构建时用 API 拉取 | 内容已在别处，或多人协作 |
| 本地笔记工具 | Obsidian / Typora 写完复制进仓库 | 已有笔记库，想顺带发布 |
| 图片存放 | 仓库内（简单，但注意 1 GB 限制）／图床 CDN（jsDelivr、Cloudflare R2、SM.MS） | 照片多、高清图多 → 建议图床 |

博客「配套功能」的常见选型：

- 评论：**Giscus**（基于 GitHub Discussions，免费无服务端）／ Utterances ／ Waline ／ Artalk
- 搜索：本地 JSON 索引（本项目已做）／ **Pagefind**（构建时生成索引，静态站首选）／ Algolia DocSearch
- 统计：Umami（自建或云）／ Cloudflare Web Analytics ／ Google Analytics
- 订阅：RSS（已有）／ Buttondown ／ Follow.it

## 四、样式与交互层

| 层 | 可选 | 说明 |
| --- | --- | --- |
| 样式 | 原生 CSS（本项目）／ Tailwind CSS ／ UnoCSS ／ Sass | 博客规模小，原生 CSS + 变量足够；组件多了再上 Tailwind |
| 组件/交互 | Astro 组件 + 原生 JS ／ React ／ Vue ／ Svelte ／ Solid ／ Preact | Astro 可以按需混用，只为需要交互的局部加载 JS |
| 轻量交互库 | Alpine.js ／ htmx ／ vanilla JS | 不引入整个框架也能做筛选、折叠、弹窗 |
| 现成主题 | AstroPaper、Fuwari（Astro）／ PaperMod、Blowfish（Hugo）／ Butterfly（Hexo） | 换栈时最省事的起点 |

本项目目前是「原生 CSS + Astro 组件 + 少量原生 JS（主题切换、分类筛选、搜索）」，这个组合在博客体量下是合理的，没有必须换的理由。

## 五、部署与加速

| 方案 | 说明 |
| --- | --- |
| **GitHub Actions → Pages**（本项目已配好） | 推送即自动构建发布，唯一需要手动做的是仓库设置里选 **Source = GitHub Actions** |
| 分支发布 | 把 `dist/` 推到 `gh-pages`；记得加 `.nojekyll` |
| Cloudflare Pages / Vercel / Netlify | 都提供免费静态托管，构建更快，通常**国内访问比 GitHub Pages 稳一些**（但仍不保证） |
| 双部署（推荐做法） | 同一份产物同时发布到 GitHub Pages + Cloudflare Pages，代码只维护一份，哪个快用哪个 |
| 中国大陆加速 | 备案域名 + 国内对象存储/CDN（腾讯云 COS、阿里云 OSS、又拍云）；不备案的话只能靠海外节点的 CDN 缓解 |

关于「国内访问」：GitHub Pages 的服务器在海外，访问速度随时段波动。如果主要读者在中国大陆，建议上线后实测，再决定是否加一个 Cloudflare Pages 镜像。

## 六、三套推荐组合

**A. 继续 Astro（推荐，改动最小）**
`Astro + Markdown 内容集合 + 原生 CSS + GitHub Actions → Pages`
已经具备：分类筛选、本地搜索（Ctrl/⌘+K）、深色模式、RSS、sitemap、404、响应式。
待做：清理示例文章、补齐个人信息（GitHub 链接/邮箱）、连上 GitHub 仓库。

**B. 想要开箱即用的博客外观**
`Hugo + PaperMod + GitHub Actions → Pages`
优点：主题漂亮、功能（标签、归档、分页、相关文章）齐全、构建极快、零依赖。
代价：要把现有页面和内容迁移一遍，Go 模板语法不直观。

**C. 想要极简与长期可控**
`Eleventy + 少量模板 + GitHub Actions → Pages`
优点：输出最干净、依赖极少、几乎没有黑盒。
代价：等于从零搭一遍，主题、搜索、RSS 都要自己写。

## 七、为什么建议继续用 Astro

1. **雏形已经可用**：构建已验证通过，页面、内容集合、搜索、RSS、sitemap、Actions 工作流都在。
2. **写作体验和「换栈派」一样好**：一篇文章一个 Markdown 文件，frontmatter 填标题/日期/分类/标签。
3. **上限更高**：以后想加交互（波形图、数据面板、小工具）时，可以在单个组件里挂 React/Vue/Svelte，其余页面仍是零 JS 的纯静态 HTML；Hugo/Jekyll 到这一步会比较痛苦。
4. **对 Pages 友好**：纯静态输出，子路径（`用户名.github.io/仓库名/`）通过 `base` 配置自动处理，不需要手改链接。
5. **换栈的真实成本**：布局、样式、搜索、RSS/sitemap、分类筛选、部署工作流都要重做一遍，收益主要是「主题更好看」——而这个用 CSS 也能解决。
